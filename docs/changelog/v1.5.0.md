v1.5.0 修的是**线上真实踩到的两个坑**，而且它们是**同一条因果链**：

- **在线更新经常失败**：文件明明下载了，版本却没变
- **反复重试之后，服务器 IP 被猫耳风控**

## 🐛 更新为什么「下载了却没成功」

根因在 **nginx 的 60 秒默认超时**。

Docker 在线更新的整条链路（下载 200MB+ 部署包 → 校验 → 解压 → `docker load` 导入镜像）
原本是在**一个 HTTP 请求里同步跑完**的。gunicorn 侧早就为此把超时放宽到了 1800 秒，
**但 nginx 没跟上**——`/api/` 那段没有配 `proxy_read_timeout`，用的是 60 秒默认值。
于是只要整个流程超过 60 秒，nginx 就回一个 504，**而后端其实还在正常干活**。

用户看到「失败」就会重试，而重试会走到更新流程开头的
`docker rm -f mismiss-online-update`，**把上一次仍在进行中的容器重建直接杀掉** ——
两次重建互相打架，栈就停在了半重建状态。

### 修法

- **更新改为后台执行**：`/api/update/apply` 与 `/rollback` 立刻返回，
  前端轮询新的 `/api/update/status` 显示进度（下载 / 校验 / 解压 / 导入镜像 / 重建）。
  长请求没了，代理超时自然不再是问题
- **进度可见**：面板会显示当前步骤；刷新页面后重新进入还能接上进度
- **同时只允许一次更新**：进行中再点会得到「已有更新正在进行中」，不再自相残杀
- **重建日志不再丢弃**：一次性容器的输出改为写入 `logs/update-recreate.log`，
  失败时终于有据可查（此前统统丢进 `/dev/null`，重试还会把容器删掉，证据一并消失）
- **进程重启后不再卡在「进行中」**：启动时若发现残留的 running 状态，
  判定为上一次被中断并如实标注
- nginx 侧也补上了超时配置，作为兜底

## 🛡️ 请求为什么会把 IP 打进风控

**每一次更新尝试（哪怕面板显示失败）都会触发容器重建 → 应用重启。**
而重启是**背靠背、零间隔**的：每个账户开机要打十来个平台接口，
20 个账户就是**上百个请求在几秒内砸出去**——正是风控最典型的触发形态。
「多次更新失败」= 反复重启 = 反复砸。

更糟的是**一旦被风控，系统会打得更凶**：

- 发送失败会附带一次 Cookie 校验，**无延迟、无上限**
- Bot 恢复失败后状态保持不变，**面板每 8 秒的轮询都会重试一次**
- WebSocket 退避在重连成功后就被清零，**抖动的连接永远停在 2 秒下限**
- **未开播房间**每轮定时消息都会"失败一次、校验一次"——
  而调用方其实早就把这种失败当预期情况静默忽略了

被风控越紧 → 请求越多 → 被风控越紧。这就是 IP 一直解不开的原因。

### 修法

**掐断正反馈**

- 预期内的业务错误（主播没开播）**不再**触发 Cookie 校验 ——
  单这一条就消掉稳态下每两分钟几十个无谓请求
- 失败触发的 Cookie 校验按账户限频
- Bot 恢复失败后进入 **5 分钟冷却**，不再被面板轮询反复触发

**降低启动冲击**

- **启动错峰**：账户之间拉开随机间隔（20 个账户从「瞬时上百请求」变为平滑铺开）
- 消除开机时**同一账户房间信息被连拉三轮**的重复
- 管理员列表按 **TTL 缓存**（原先注释写着「仅调用一次」，实际每次刷新都调）

**全域护栏**

- 新增**出站闸门**：所有发往平台的请求都过一次全进程限速（默认约 10 请求/秒），
  将来任何新增代码路径也绕不过去
- 平台明确报限流时触发**全局退避**，所有账户一起冷却 —— 宁可少发消息也不再猛打
- WebSocket 重连加抖动，并修掉「秒断秒连时退避永远停在 2 秒」的问题
- 定时消息加抖动，账户之间不再同一瞬间齐发
- 全局消息广播时账户之间拉开间隔
- HTTP 连接复用：不再每个请求都重建 TCP + TLS

## 🔢 账户编号为什么会有断号

如果你看到账户列表里 **#25 的下一个直接成了 #27**，原因在这里：

创建账户时，编号是**在任何校验之前**就被占用并自增的。于是只要后面任何一步失败——
**用户名重复**、密码太短、Cookie 无效、运行时启动失败——那个编号就被白白吃掉了，
而且**永远补不回来**。你推测的「用户名重复时自动创建了一个不存在的编号」完全正确。

顺带还有更隐蔽的一处：Cookie 无效被拒时，账户记录**已经进了内存**，
异常直接冒泡出去，于是留下一个「面板说创建失败、账户却真实存在」的幽灵记录。

### 修法

- **占号挪到全部校验之后**，并在任何后续失败路径上把编号还回去
- Cookie 无效时**彻底回滚**：停运行时、删目录、移除记录、回退编号
- **创建弹窗里输入用户名时就告诉你是否可用**（防抖查询），
  不再等提交后才弹「已被使用」

### 新增：一键重排编号

管理端账户页在有断号时会多出一个「**重排编号**」按钮：

- 点击后先弹出**新旧编号对照表**让你确认，不会闷头就改
- 确认后把编号压紧为连续的 1..N
- 账户名称、直播间、Cookie、插件配置**都不受影响**；
  登录令牌里记录的账户编号会同步改写，已登录的账户用户不会被踢下线
- 重排会重启全部账户（所以顺带走启动错峰），期间面板短暂不可用

断号是历史遗留，往后不会再产生新的。

## ⚙️ 新增配置（`config.yml`）

```yaml
ratelimit:
  startup_stagger: 1.5    # 启动时账户间平均间隔（秒）
  broadcast_gap: 0.4      # 广播全局消息时账户间平均间隔（秒）
  min_interval: 0.1       # 全进程最小请求间隔（秒），0.1 ≈ 上限 10 请求/秒
```

**账户越多越该调大 `startup_stagger`**；20 个账户以上建议 2~3 秒。
不写这一段也能跑，全部有内置默认值。

若从日志里确认到猫耳专用的限流错误码，可用环境变量临时补充识别特征，
不必改代码：

```bash
MISMISS_RATE_LIMIT_MARKERS=你的错误码
```

## ⚠️ 升级须知

**这一版必须手动更新一次。** 当前版本仍有缺陷（就是上面那个 60 秒超时），
走面板很可能再次半途而废。在服务器上执行：

```bash
cd /opt/mismiss                    # 换成你的部署目录
docker load -i mismiss-docker.tar.gz
docker compose --env-file .env -f docker-compose.yml up -d --force-recreate
```

之后往后的版本就可以正常走面板在线更新了。

**如果服务器 IP 正在被风控**，先让它安静一会儿再升级——升级会触发一次重启，
也就是一轮启动请求。可以先停掉应用容器止血：

```bash
docker compose --env-file .env -f docker-compose.yml stop mismiss
```
